## 直近実行：最初の2〜4セッション（候補者人数未確定）

この節は数人の協力見込みがある場合に使う **開始手順**。実在する参加者が確保されたという記録ではない。まだ招待送信・日程確定・実測はいずれも0件。

### 優先する案件の振分け
- 協力者1人目：部屋探し・通勤／在宅勤務の生活が話せる人なら **KIDP-004**、関心や目標について答えられる人なら **KIDP-003**。どちらにも該当する場合は未充足の案件を優先。
- 協力者2人目：可能なら別案件へ割り当て、**各案件で最初の有効データを1件ずつ**取る。
- 協力者3〜4人目：各案件の不足している生活タイプ／関心タイプを補う。原則1人1案件。
- 5人以上すぐ集まる場合も、最初の2セッションを実施して記録手順を点検してから残りを順次行う。**P0指標や閾値は途中変更しない**。
- 誰も該当しない属性の枠へ無理に振り分けず、候補台帳の target_profile に合う枠を選ぶ。候補ID（A01など）と案件別参加者ID（P01など）は混同しない。

### 候補者を確定する際の最小確認
1. 参加意思と連絡手段。候補者本人の氏名・連絡先は公開GitHubに書かない。
2. 案件に応じ、Aは通勤／在宅／夜型および部屋探し経験、Bは目標の明確さ・自己分析への関心を確認。
3. 企画内容を事前にどの程度知っているか、利用端末（スマホ／PC）、15〜20分を確保できるか。
4. 候補の都合に合わせて日時を確約し、候補IDの台帳行だけを **NOT_SENT → INVITED → CONFIRMED** と実際の進行に応じて更新する。招待未実施ならNOT_SENTのまま。
5. 企画を知らない中立参加者を各案件2人以上含められるかを同時に点検する。

### セッション実行時の5ポイント
- **同意**：運営者が記録する項目、任意参加・途中中止を説明し、記録に同意を得る。
- **観察**：参加者を誘導せず自由に操作してもらう。最初の反応は可能なら原文で記録。
- **CSV回収**：テスト画面からCSV行をコピーし、ブラウザ外の非公開保存先に保存。未回収ならDONE不可。
- **状態登録**：進行役の同じブラウザの Test Ops でCSV回収済みをチェック後DONE、無効条件が成立すればINVALID。
- **保留**：初回1〜2件で仮説を変更せず、案件ごとに有効5件でReview判定を確定する。

### テスト直後に残す内部ログ（実際の回答が出るまでは空欄）
案件ID / 参加者ID / 日時 / 使用端末 / 募集元 / 企画の事前理解（有・無） / 実施完了・INVALID理由 / CSV回収の有無 / 第一声 / 中立質問への回答 / 次の実施枠。

CSV行や自由記述に名前・住所・連絡先などを含めない。公開GitHubには集計結果に限定した資料を残し、生の観察ログは非公開で管理する。

## Step 1 — 対象者を見つける（募集順序）
1. 知人、学校関係者、元同僚などで候補16枠を埋める。すべての候補が知人である必要はない。
2. 参加候補のタイプを確認する。Aは通勤2・在宅/Hybrid2・夜型1。Bは目標明確2・曖昧2・自己分析に消極的1。
3. Aは5人中3人以上が部屋探し/引越し経験者、うち1人以上は過去3年以内。Bは自己分析利用者・非利用者を混ぜ、キャリア以外への関心がある人を1人以上。
4. 「この試作品の設計内容を既に知っているか」を確認し、知らない人をA・B各2名以上確保する。**知人であっても企画を知らなければ対象になり得る**。
5. 確約前に候補ID、参加可能な案件、日程、利用端末だけを照合する。案件間で参加者の重複は原則避ける。
6. 偏り・欠員が出た枠のみ予備候補または中立的な外部募集に切り替える。

## Step 2 — 招待文（宛先は本人の確認後、手動送信）

### A: 駅生活圏（15分程度）
「制作中のWeb試作品について、15分ほど操作に協力してもらえませんか？架空の3つの街を見比べる内容で、部屋探し経験の有無は問いません。操作しながら分かりにくい点や率直な感想を伺います。正解はなく、途中でやめても大丈夫です。協力できそうなら都合のよい日時を教えてください。」

### B: LIFE DESIGN LAB（18分程度）
「制作中のWeb試作品について、18分ほど操作に協力してもらえませんか？『やってみたいこと』に関する20個のカードを選ぶ簡単な内容です。性格診断ではなく、画面の分かりやすさと率直な感想を確かめています。正解はなく、途中でやめても大丈夫です。協力できそうなら都合のよい日時を教えてください。」

### 返信がない場合（最初の依頼から48〜72時間後、1回のみ）
「先日お送りしたWeb試作品の操作テストの件です。15〜20分程度で、参加は任意です。難しければ返信不要です。ご都合が合いそうなら教えてください。」

**招待時点では事前に主要な仮説や成功指標を説明せず、Pxx URLも確定するまで配布しない。** 謝礼を出す場合は実際の金額・方法を明示する。現時点では報酬額を確定・約束しない。

## Step 3 — 実施日程（運用目標、確約日ではない）
- Day 0：候補16枠を埋め、まず適合する10名へ招待を出す。辞退や未返信があれば予備枠へ追加依頼。
- Day 1–3：返信・条件確認・日時確定。面談はAが15分、Bが18分 + 前後5分のバッファ。
- Day 2–7：オンライン/対面で進行役付きP0テストを実施。1人につき1案件・1セッションを基本とする。
- 各案件で有効5件を満たした時点：ReviewでDecisionを保存。先に閉じたActive SlotをWHYNOTへ渡す。
- 想定期間は計画上の目標であり、募集率や参加人数を保証しない。

## 無効・辞退時の補充ルール（P06–P10）

- P01〜P05にINVALIDが生じても、そのIDを別人に使い回さない。Test Opsで「追加参加者 P06〜P10」を開き、未使用のPxxを新しい協力者に割り当てる。
- 例：P01〜P04が有効、P05がINVALID、P06が新規実測・CSV回収済みDONEなら、有効5件を集計できる。
- 予備候補ID（A06/B06など）と参加者ID（P06など）は別。承諾前に同じ番号だと仮定しない。
- 予備Pxxの個別リンクは進行役のTest Opsから開く。旧PDFにP06〜P10のQRがない場合も新規IDを再利用で代用しない。
- Test OpsとReview Toolは必ず同じ進行役ブラウザで使用する。CSVは別途非公開保存する。

## Step 4 — 実施フロー（Pxxごと）
1. 開始前に口頭で目的・記録内容・途中中止の自由を説明し、記録について同意を取る。録音・録画や追加の個人情報は別途同意がない限り扱わない。
2. Test Opsで対象案件のP01–P05を選び、個別URLを開く。**テストURLは特定の参加者にのみ配布**する。
3. 開始時は固定オープニング以外の説明をせず、操作を観察。誘導質問・操作の手助けを避ける。
4. セッション後、定型評価と第一声をテスト画面に入力する。否定的な意見や途中離脱は、それ自体を自動的にINVALIDとしない。
5. CSVをコピーし、ブラウザ外の安全な場所に案件別・Pxx別に保存。公開リポジトリに実データをコミットしない。
6. Test Opsの「CSV行をブラウザ外に保存済み」にチェックしてからDONE。検証不能・データ欠落はINVALIDとし理由を記録。
7. 各案件で有効5人分がそろったら、**同じブラウザのReview Tool**でヘッダー付きCSVを集計。TEST_SUMMARYを保存し、事前固定ルールでDecisionを確定する。

## 測定時の品質ゲート
- Candidate ID (A01など) と Participant ID (P01など) は別物。Pxxは **案件内で重複禁止**。
- DashboardのDONEは進行役によるCSV回収確認であり、ファイル存在や本人確認の自動検証ではない。
- REVIEWは同一ブラウザのlocalStorageを参照する。別端末のCSVは手動で回収・統合し、進行役のブラウザで状態を確定させる。
- 5件に到達しても、多様性条件と中立参加者2件を満たさない場合はDecisionの解釈に留保をつける。
- SAMPLE/QAデータを実測結果へ混ぜない。実測データには本人や第三者を特定する記述を残さない。
- Prototypeが動かない、個人情報・安全上の重大懸念が出た場合は一時停止して修正を優先する。
