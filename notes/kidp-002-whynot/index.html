KIDP / PROTOTYPE2026.10.07

「解決策」より先に
「困りごと」を集めたらどうなる？
――WHYNOTを設計してみた

世の中にはアイデアを投稿する場所はたくさんある。でも、その一歩手前にある「これ面倒」「なんでこうなんだろう」だけを集めたら、次に作るものを探す材料になるんじゃないか。

KIDP-002PROJECT STATUSPROTOTYPE ↓
これは市場調査の結果ではありません。

WHYNOTはConcept Prototypeです。AI分析やBuild Scoreは「仮説を作るための仕組み」であり、需要・市場規模・事業価値を証明するものではありません。

CONCEPT

Problemを、次の制作物の入口にする。

これ面倒→Problem→AI Structure→SAME→Solution Lab→Build Score→KIDP→Prototype

重要なのは、Solutionを先に置かないこと。まず「誰が・いつ・どのくらい困るのか」をProblemとして残す。

きっかけは「アイデアの在庫」だった

「こんなアプリがあったら面白い」「この仕組み、別の業界でも使えそう」。思いつきは増える。でも、アイデアから始めると、そのアイデアを成立させる理由を後から探し始めてしまう。

そこで順番を逆にしてみた。アイデアではなく、解決されていないProblemを先に貯める。 そこから必要に応じて複数のSolutionを生やす。

「何を作りたいか」ではなく、「何がまだ面倒なのか」から始める。

最初の設計は、たぶん「Like」が強すぎた

Problem投稿サービスを考えると、Like、コメント、ランキングを置きたくなる。でもLikeでは「面白い問題だと思った」のか「自分も実際に困っている」のかが分からない。

そこで反応をSAMEに変えた。意味は「私にもこのProblemがある」。人気投票ではなく、Problemの重なりを取るためのボタンにした。

CHANGE 01LIKE → SAME

評価ではなく「自分にもある」を取る。Prototypeでは1ユーザー1Problemにつき1回だけ。

ProblemとSolutionを同じ投稿に入れない

もう一つ分けたのがProblemとSolutionだ。「閉店作業が長い」というProblemに対して、チェックリストSaaS、物理キット、外部BPOなど、解き方は複数あり得る。

Solutionを投稿の主役にすると、議論が「その案が好きか嫌いか」に寄る。Problemを資産として残しておけば、一つのProblemに何度でも別のSolutionを接続できる。

PROBLEM飲食店の閉店作業に毎日45分かかる

誰が / いつ / 頻度 / 現在の回避策 / Pain

SOLUTION LABCloseFlow / Closing Kit / NightOps

SaaS / 物理＋デジタル / BPO

AIに「答え」を出させるのではなく、Problemを整理させる

投稿時に必要なのは、きれいな企画書ではない。「閉店作業で帰るのが遅くなる」くらいでいい。Prototypeでは、その雑な文章をProblem / Who / When / Frequency / Workaround / Painへ整理する画面を置いた。

ここでもAIの出力は事実ではなく仮説として扱う。特に「なぜ未解決なのか」「既存サービスの穴は何か」は、実際には追加調査が必要だ。

Build Scoreは、事業性スコアにしなかった

途中で最も危なかったのがスコアだった。SAMEが多く、AIが面白いと言えば「事業価値90点」のような数字を出したくなる。でもPrototype段階でそんな精度はない。

そこでBuild Scoreの意味を限定した。K. Aitoで設計・Prototype化すると面白いか、検証しやすいか。 それだけを100点で見る。

BUILD SCORE87制作適性

一言で伝わるか / 独自メカニクス / UI映え / Prototype可能性 / 実際に検証できるか / 派生性など。

NOT BUSINESS VALUE
NOT MARKET SIZE
NOT INVESTMENT SCORE

実際に、触れるところまで作った

今回は仕様書だけで終わらせず、20件のProblemを入れたレスポンシブWeb Prototypeまで作った。HomeからProblemを眺め、SAMEを押し、自分のProblemを投稿し、AI構造化Demo、Analysis、3つのSolution、Build Score、Build Queueまで一続きで触れる。

01HOMEProblemを眺める
02SUBMIT雑な困りごとを入力
03STRUCTUREProblemへ整理
04SOLUTION LAB複数案を比較
05BUILD QUEUE次に作る候補へ

本番用のアカウント、Backend、課金、コメント、DM、リアルタイムAIは入れていない。今回確かめたいのは「このProblem DBを触っていると、自分のProblemも入れたくなるか」だからだ。

Prototype内のSAMEはブラウザ内だけに保存されます。実データ・実AIには接続していません。

Project GIVEを、後付けではなく「実績」にした

WHYNOTだけを見ると「Problemから本当に何か作るの？」という疑問が残る。そこでKIDP-001 Project GIVEを接続した。

クーポンを使わず失効する→Problem→Project GIVE→BUILT / KIDP-001

Project GIVEはWHYNOTより先に設計したものだが、逆にたどれば「使わないクーポンが失効する」というProblemから生まれたSolutionとして扱える。これを最初のBUILT例にした。

作ってみて、WHYNOT自体のProblemも見えた

Problemを集めれば価値が出る、とは限らない。同じProblemの重複、抽象度の違い、単なる愚痴、個人情報、誹謗中傷、危険な投稿。「未解決」と書くなら既存サービス調査も必要になる。

本番化するなら、semantic clustering、重複統合、moderation、報告機能、出典管理、AIコスト制御などが必要だ。むしろPrototypeを作ったことで、「Problem DBを作るProblem」が具体的になった。

次に確かめるのは4つだけ

機能を増やす前に、まず人がこの体験を面白いと思うかを見る。

  1. 01Problemを3件以上見たくなるか
  2. 02SAMEを押したくなるか
  3. 03自分のProblemを投稿したくなるか
  4. 04「これ、本気で作ったら？」まで見たくなるか

ここが弱ければ、AI機能や事業モデルを足しても意味がない。KIDP-002は現在Prototypeまで。次はTestで壊す。

今回の設計で残ったもの

  • Idea-firstではなくProblem-firstにする
  • LikeではなくSAMEで「自分にもある」を取る
  • ProblemとSolutionを分離する
  • AI出力は答えではなく仮説として表示する
  • Build Scoreを事業価値から切り離す
  • Prototypeは検証したいCore Loopだけ作る
  • Project GIVEをProblem→Buildの実例として接続する
