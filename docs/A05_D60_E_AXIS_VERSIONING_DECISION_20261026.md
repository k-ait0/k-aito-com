## 1. E軸の3方式比較

| 方式 | 定義 | 利点 | 重大なリスク | 現段階の判定 |
|---|---|---|---|---|
| E-A：補助的な相対選好 | 必要な生活費・休息が確保されたと仮定し、追加的な金銭裁量と時間裁量の優先度を尋ねる | 既存UIの比較形式に近い | 6問の同義反復、比較量の非等価、生活状況への依存、二極化の妥当性未証明 | **認知面接の比較対象**。採用未承認 |
| E-B：独立した2尺度 | 金銭的な追加裁量の希望と時間的な追加裁量の希望をそれぞれ評価 | 両方を強く希望する人を表現できる | 回答数・採点・欠損処理・32派生分類との互換が崩れる | **構造再設計の対照案**。採用未承認 |
| E-C：タイプ分類から除外 | 4軸16タイプだけを表示し、金銭／時間の希望は任意の振り返りにするか削除 | 未検証の補助分類を確定的に提示しない | 既存の32派生方向性と仕様差が生じる | **リスク低減の対照案**。採用未承認 |

**暫定的な実装優先順位：E-Cを安全側の対照案として設計、E-A/E-Bは研究で比較。** これはE-Cの採用決定ではない。現行版のE採点・結果・保存形式を変更しない。E05の月3万円／週3時間は次版候補から除外。

## 2. 現行コードで確認した互換性制約
- `questions.mjs` の `QUESTION_SET_VERSION` と `canonicalQuestionManifest()` / `questionSetHash()` は表示順・左右方向・文言を含む。文面の変更はハッシュ変更を伴う。
- `engine.mjs` の `validateQuestions()` はA〜E各6問、合計30問を必須とする。E-B/E-Cで問数を変える場合、現行関数へ無断流用できない。
- `scoreAssessment()` は5軸の集計を行い、`derive()` はA〜DからT01〜T16、Eからmoney/time/neutral/withheldを導く。E-Cでは結果契約も変更が必要。
- `newDraft()` と `verifyDraft()` は質問・採点・タイプ・コンテンツの4版と質問ハッシュを照合する。旧ドラフトを新ルールで開かない。
- `makeSnapshot()` は結果とタイプ説明をsnapshot.presentationに複製する。`classifySnapshot()` は現行版の内容まで厳格に照合し、別版はlegacy扱いにする。新タイプ文言を現行`types.mjs`へ直接上書きすると、旧版保存結果の整合性を壊し得る。

## 3. 新版を実装する場合の境界
1. 現行の`questions.mjs`、`engine.mjs`、`types.mjs`を不変として残す。v2専用の独立ファイル群に質問・採点・表示定義を分離する。
2. 質問の表示順、ID、axis、direction、left、rightを固定してSHA-256を計算する。版とハッシュの両方をスナップショットへ保存。
3. 採点アルゴリズム変更ならSCORING_VERSION、16タイプの構造変更ならTYPE_VERSION、説明文変更ならCONTENT_VERSIONをそれぞれ更新。単なる文言変更でも旧版presentationを上書きしない。
4. E-B/E-Cの結果を現行の`wealth`列へ偽装して格納しない。結果スキーマを別版とし、読み込み時は明示的なディスパッチで分類する。
5. 旧版スナップショットはread-onlyで保持し、移行・再採点・上書き・自動修復を禁止。未知版や不整合データは隔離する。
6. A01 / MY LIFE NOTE連携は受け手が質問・採点・タイプ・コンテンツ・結果スキーマを受容すると確認できるまで停止。

## 4. 実装前に必要なテスト仕様
- 同一版・同一manifestのSHA-256一致、文言/順序/左右変更時のハッシュ不一致
- 30問と異なるE-B/E-Cの設問を旧`validateQuestions()`へ誤投入した場合の明示拒否
- 旧ドラフトの版不一致による拒否、旧snapshotのlegacy read-only判定
- `wealth`と新E形式の誤変換拒否、Eを未回答としたときの4軸タイプ分類の独立性
- 全16タイプのID/グループ/4軸符号と新版説明文の一致
- 旧版データの保存・エクスポート・復元プレビューの後方互換
