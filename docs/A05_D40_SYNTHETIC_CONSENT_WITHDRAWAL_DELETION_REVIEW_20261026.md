## 2. 全9件の検証シナリオ

| シナリオ | 想定 | 期待する安全上の動作 |
|---|---|---|
| `consent-refused` | 同意を辞退後、回答メモ作成を試行 | メモ・連絡先を作らない |
| `consented-withdrawal` | メモ・連絡先の仮同意後、翌日に撤回 | 照合できる仮定の下でメモ・連絡先・対応表の**架空マーカー**を消す |
| `withdrawal-after-contact-expiry` | 14日経過後、対応表はまだある時点で撤回 | **検証済み本人トークンがあるという仮定**の下でのみ、削除可能なケースを表示 |
| `unverified-withdrawal` | 本人照合できない撤回依頼 | 誰の記録か確証がないため、個票の削除成功を宣言しない。要人手審査 |
| `withdrawal-after-link-expiry` | 30日超、対応表なし、メモは90日以内 | 個別メモを特定できない。**削除完了とは判定しない** |
| `retention-deadlines` | 14/30/90日の各境界到達 | 連絡先→対応表→メモを順に**論理的に失効**させるだけ |
| `repeat-withdrawal` | 先に撤回した後、再度撤回 | 繰り返し実行してもデータが復活しない |

| `withdrawal-before-consent` | 参加前に中止希望、その後に同意を試みる | 中止状態を勝手に解除せずメモ収集しない |

**重要な前提**：「照合可能」とは参加者が事前に合意した認証・照合方法を通じて権限が確認できる場合に限る。D-40は本人確認用トークンを発行・検証していない。削除可能シナリオは**実際に実現できる証明ではない**。

## 3. 発見した設計上の未解決問題

### A. 連絡先と回答記録の同意を分離する

「メモ記録に同意」だけで募集連絡先の保存を正当化しない。シミュレータでは別の `consent-contact` がある時だけ連絡先マーカーを立てる。研究用仮名ID対応表についても、何を記録するか参加者説明と実務判断を必要とする。これは実利用者の同意を取得したことを意味しない。

### B. 14日以降の撤回と本人照合

連絡先が先に消えても、30日目までは対応表が残るという提案だった。しかし**本人が研究用ID/撤回トークンを保持し、相手が適切に照合できる仕組みがなければ**、対応表だけでは依頼者を特定できない。本人確認方法、トークン漏えい時のなりすまし、誤消去防止、撤回の期限をG1-05・G1-09で決めるまで「撤回できる」と約束できない。

### C. 対応表30日・メモ90日の矛盾

30日後に対応表を消すと、個人の記録を90日残している間も**特定の人の削除依頼と対応づけられない**可能性がある。これは以前から識別していた問題で、D-40では削除成功を返さない動作を確認した。

選択肢として、**(i) 対応表の期限を本人が個別撤回できる期間と揃える**、**(ii) 個票・メモを30日以内に非識別集計へ移行して消去する**、**(iii) 照合可能なトークンを安全に配布・管理し、本人へ期限を明示する**、**(iv) 保存と撤回の仕組みが整うまで記録をやめる**、を改めて比較すべき。いずれも未決定であり、期間だけで合法性や安全性が確定するものではない。

### D. 同意後の撤回・記録の復活防止

中止・撤回後に同じ面接内で同意操作があっても、同意を自動復活させてはならない。再参加は募集・同意と保管上の条件を**新しい承認済み手順**で検討する。

### E. 「消去した」は技術的な確証が必要

純粋関数はデータベース、OSのごみ箱、端末バックアップ、クラウド同期、複製先、外部文字起こしサービスの消去を試していない。実運用へ移す場合、利用する私的領域を定め、権限・暗号化・連絡先の分離・バックアップも含めた削除試験と監査証跡が必要。
