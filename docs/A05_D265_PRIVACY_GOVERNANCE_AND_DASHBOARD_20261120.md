# A05 D265｜分析管理画面の研究版・データ取得開始前の運用設計

**状態：管理画面は合成データ専用の研究版。プライバシー・アクセス制御・本番収集条件は提案であり未承認。**

## 1. D265の範囲

D261の集計設計→D264の純粋な集計関数・一時PostgreSQLテストを引継ぎ、**設問品質・16タイプ分布を確認する管理画面**の外観・動作を、架空データだけで検証する。

- 成果物：`research/a05/d265-synthetic-dashboard-template.html`、合成データ生成器 `scripts/a05-d265-build-synthetic-dashboard.mjs`、ブラウザテスト `scripts/test-a05-d265-synthetic-dashboard.cjs`。
- 統計の元：D264 `buildOfflineQualityRollups`。シード固定・非出題の設問は分母に含めない。ダッシュボードに書き出すのは日別集計数と設問定義、編集候補のみ。**提出ID・個別回答・顧客情報は出力しない**。
- 表示内容：診断バージョン切替、JST期間切替、30問時／Y/N後の分類切替、全完了者／単独分類者の分母切替、T01〜T16の出現割合、複数候補・情報不足、30問各設問の1〜7・UNKNOWN・NOT_APPLICABLE、補助Y/NのYES・NO・UNSURE・NOT_ANSWERED、手動レビュー候補。
- タイプIDは**合成された模擬分類**であり、実回答に対するD255の正しい判定分布を示さない。テスト用仮閾値の編集候補も実運用判定ではない。
- 研究プレビューへの接続は静的HTMLの閲覧だけ。CSPで`connect-src 'none'`、画像・オブジェクトも不可。ログイン機能・保存・API・実DBはない。
- **公開上の重要な区別**：研究プレビューは誰でも開けるURLである。合成データしか載せない。**将来実データの管理画面を同じGitHub Pagesの公開パスに配置してはいけない**。実運用管理画面には独立した認証・認可付きのサーバー基盤が必要。

## 2. 実回答収集を始める前に確定すること

### 同意と個人情報保護

- ユーザーの診断機能の利用は**回答データの提供に依存させない**。結果表示までは送信を必要としない。
- 「品質改善・出現分布の分析のため回答を匿名化に配慮して利用する」こと、**各回答・スキップ理由・診断版・算出した参考分類・送信日時**を収集する予定であること、同意しない場合も診断結果を見られることを、送信前に明確に説明。
- 提供は初期OFF、明示的な任意同意でのみ最終送信。実装時は同意文面の改訂版ID・同意日時を同じ提出に紐付け、サーバー側で検査。**クリックの有無だけを自己申告するクライアント値を、サーバーが無検証で信頼してはならない**。
- 「匿名」と断言せず、回答組合せ、IP・ブラウザログ、時刻による再識別の可能性を評価する。Web/APログと分析DBの結合は禁止を原則とし、ログ側の収集・マスキング・保持も別途設計。
- 法令適合性・開示文言は、公開前に日本の個人情報保護法および利用する外部サービスの利用条件に照らして別途点検する。**本書のみで適法性を保証しない**。

### 保持期間・削除（未承認の初期提案）

| 対象 | 仮の保持期限 | 扱い |
|---|---|---|
| 個別の提供済み回答・設問の版 | **90日** | 目的達成後の削除バッチ、同意撤回・削除申出に対応する設計 |
| 提出受領の重複防止キー | 個別回答と同期間、削除に伴う整合性を考慮 | 推測困難な提出IDとワンウェイに処理したキー |
| 再識別リスクを評価した日別集計 | **最大24か月** | 低件数の公開防止、個人の回答再構成を避ける |
| 管理者の閲覧・操作ログ | **90日を仮置き** | 最小限の監査記録、回答本文を含めない |

上記の期間は**仮案であり実際の保存設定ではない**。集計結果から個人寄与を差し引く必要がある削除請求の場合、個別回答削除後の派生集計再構築方法を設計し、集計の性質と撤回時の影響を説明する。

### 削除を申請するための受領トークン案

- ログインを必須にしない場合、ユーザーには送信後1回だけ推測困難な削除用トークンを表示し、サーバーに置くのはそのハッシュと失効時刻のみとする。
- トークンの再発行ができない場合の対応方法、紛失時に本人の識別情報を追加徴収しない方法、削除済みの確認方法を設計。
- 送信中はアクセスログ・ブラウザ履歴・Refererにトークンを含めない。URLパラメータとして送らない。
- 削除が集計に反映されるまでの一貫性とエラーハンドリングをテストするまでは公開しない。

## 3. 権限・通信・本番ダッシュボード

| ロール | 可能な操作 | 明確な禁止 |
|---|---|---|
| visitor | 診断結果閲覧、任意提供を判断 | 管理統計の取得、回答の横断検索 |
| ingestion-service | 同意済み回答の検証・1回保存 | 集計閲覧、任意の管理権限 |
| aggregator | バージョン別の統計更新 | 生回答の一般公開、設問の入れ替え |
| reviewer | 集約済み設問品質・タイプ分布の閲覧、レビューコメント | 生回答の全件ダウンロード、直接本番差し替え |
| publisher | 独立した編集承認を経て設問版を公開 | レビュー閾値だけでの自動採用 |
| security-admin | 役割付与、失効、監査ログの管理 | 権限を使った統計内容の無制限共有 |

**本番ダッシュボードはID管理・多要素認証・サーバー側アクセス制御・監査ログを必須とする設計案**。ブラウザにDB接続文字列、API管理キー、個別回答を埋め込まない。権限を有する管理者への集約済みデータ提供も、最小件数（例：n>=20、仮置き）の公開範囲を検討する。

- 送信API（未実装）：必須の`questionnaire_version`／有効な出題30件／有効回答値／最大8件のY/N／同意版をサーバー側で検査。採点結果は権威のあるサーバー側ロジックで再計算し、クライアントの`typeId`をそのまま信用しない。
- 重複防止：一時的ランダム提出IDとDB一意制約、競合する再送への拒否を実装。送信前の回答データは既存UIと同じく端末外へ自動送信しない。
- 本番管理画面：TLS・サーバー側認可・最低限の集計API・ロール別アクセス・アクセス追跡・低頻度セルの抑制ができるホスティングを別途選定。静的Github Pagesには**絶対に本物の集計値を公開しない**。
- バックアップ・暗号化・秘密情報のローテーション・復旧試験は本番導入前のゲートとする。

1. 画面と集計テストの受入（D265：**合成データのみ**）。実機スマホ・アクセシビリティも別途評価。
