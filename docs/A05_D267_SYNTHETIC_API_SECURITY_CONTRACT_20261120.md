# A05 D267｜合成データ専用APIと一時PostgreSQLの統合検証

**状態：SYNTHETIC_EPHEMERAL_SANDBOX_ONLY / NO_PRODUCTION_DEPLOY / CONSENT_NOT_APPROVED / REAL_RESPONSE_COLLECTION_DISABLED**

## 目的と不変条件

D261のDB草案、D264の集計仕様・PostgreSQL検証、D265の合成専用管理画面を維持し、**合成回答を処理する一時APIとPostgreSQLの整合性**を実際に試す。通常公開版、A05 Ver.1〜2.2、D265管理画面は変更しない。GitHub Pagesに新規APIを公開しない。

成果物：

- `research/a05/analytics/d267_ephemeral_api_schema.sql`：固定30問＋補助Y/N2問の合成データ・受領レシート・最小監査テーブル（PostgreSQL 16のテストサービスのみ）。
- `scripts/a05-d267-synthetic-api.mjs`：起動メソッドを持たないHTTPリクエストハンドラー。プロセス外でリッスンする処理はない。
- `scripts/test-a05-d267-synthetic-api-integration.mjs`：GitHub Actions内でHTTPを127.0.0.1のランダムポートに立て、PostgreSQLの一時コンテナへ接続し、正例・負例・削除後再集計を検証。
- `.github/workflows/a05-d267-synthetic-api-postgres-ci.yml`：読み取り権限のGitHub CI、他の公開ファイルのハッシュ検査、テスト終了時の一時DB自動破棄。

## 運用境界

- CIでのみ`A05_D267_SANDBOX_MODE=synthetic-ephemeral-ci`を指定。モードを設定しないとハンドラー生成自体が失敗。
- HTTPサーバーは統合テストが `127.0.0.1` の一時ポートに作る**試験用ローカルプロセス**のみ。クラウドサービスや通常サイトへ配備する定義はない。
- DBに保存するのは既知の`D267_SYNTHETIC_CI`というバージョン、固定30件のダミー設問と最大2件のダミーY/N、`D267_EPHEMERAL_FIXTURE_NOT_REAL_RESPONDENT`の明示的な合成センチネルを満たす入力のみ。
- CI内の認証トークンはテスト実行時に乱数生成。リポジトリやクライアント側HTMLには書かない。
- PostgreSQLはGitHub Actionsの使い捨てDockerサービス。サンプル用DB接続パラメーターはテスト環境のみ。本番DB接続文字列や利用者の回答履歴には接触しない。
- 本番診断Webは `connect-src 'none'`を維持。合成APIを参照するコードを含めない。

## テスト用HTTP契約

| メソッド・パス | 認証 | 役割 | 内容 |
|---|---|---|---|
| `GET /health` | なし | なし | 合成APIであることだけを返す |
| `POST /v1/synthetic/submissions` | Bearer | ingestion-service | 30問＋任意の最大2 Y/N・合成センチネル・仮同意の厳格検査／保存／集計更新 |
| `DELETE /v1/synthetic/submissions/:submissionId` | 推測困難な削除トークン | 受領者（合成） | トークンをヘッダーに送り、関連回答を物理削除→集計を同一トランザクションで再構築 |
| `GET /v1/synthetic/admin/metrics` | Bearer | reviewer | 日別ソース由来の集計ビュー（個別回答は返さない） |
| `POST /v1/synthetic/admin/rebuild` | Bearer | aggregator | 残存セッションから設問・タイプ両集計を再生成 |
| `GET /v1/synthetic/admin/audit` | Bearer | security-admin | 操作種別・ロール・結果別の監査件数（個人情報・トークン・回答は含めない） |

**あくまで技術試験上のロール**。Bearerトークンによる簡易アクセス制御は、本番に必要な本人認証・MFA・セッション管理・CSRF/レート制限・SQL権限分離の代替ではない。

## DB/APIの統合保証範囲

- `assessment_submissions`／`question_exposures`／`classification_snapshots`へ保存し、`daily_question_counts`／`daily_type_counts`を**DB上の現存レコードから**再集計する。クライアントが任意の集計値を送る機能はない。
- セッション二重送信は、提出UUID・冪等キー・入力ハッシュで検査。同一内容は再集計せず200、矛盾や削除済み提出は409。初回だけ削除トークンを返し、DBにはSHA-256ダイジェストだけを保存。
- データ削除は関連回答・分類結果をカスケード削除、計数テーブルを再計算、受領レシートを`DELETED`状態に更新し、ペイロード・削除トークンのハッシュを消す。再送不能な墓標はテスト用一時DBが消えるまで残る。本番での墓標保持期間は未決定。
- 行全体のDB監査には提出ID・削除トークン・IP・UA・本文を残さず、ロール／操作／成否／変更件数のみ記録。
- 不正な回答形式、30問不足・出題順の不一致、異なる版、未承認の別入力フィールド（例：メール、クライアント発行の分類結果）、実際の同意であるかのような入力は拒否。
- **最重要の限界**：D267の分類は明示的に**テスト用の疑似ロジック**（合成例T01/T02/未確定）であり、D255分類エンジンとは接続していない。したがって、DBの16タイプ分布がD255と一致することや実測の診断精度は**この段階では保証できない**。ただし30問時／Y/N後と未確定者の分母・ソースはSQLビューで検証する。

## セキュリティ・プライバシー上の未実装事項

**合成データのCIが通ることは、本番運用の許可ではない。**

1. 実利用者向け任意の回答データ提供同意UI（初期OFF）、利用目的、取得項目と送信頻度・合意の証跡、撤回時の説明。
2. 本物の診断採点／D255分類をサーバーで独立再計算する経路、版・マニフェスト整合性の正確な検証（D267は合成の固定30問のみ）。
3. 個別回答90日、集計24か月などの保持案の正式承認と削除ジョブ。期限・バックアップ・再識別・集計撤回の扱いも決定。
4. 公開APIのTLS終端、管理MFA、最小権限のDBロール分離、WAF・頻度制限・CSRF/CORS/セキュリティログ・秘密情報のローテーション。
5. 個別回答を含む管理画面の非公開設計、集計の低件数セル抑制。**D267の集計APIは合成データだけなので小集計を抑制していない。これを本番に流用しない。**
6. 実利用環境の法務・安全性・障害復旧検証と、ユーザーによる明示の別承認。

**禁止**：D265の公開GitHub Pagesに実測値や秘密情報を追加すること、D267ハンドラーをインターネット公開して実回答を受け取ること、仮同意センチネルを正式な同意とみなすこと、品質レビュー候補から設問を自動変更すること。
