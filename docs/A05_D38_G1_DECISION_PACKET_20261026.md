## 4. 自動チェックの意味と上限

`inspectG1Readiness(register)` は以下を検査する**読み取り専用の純粋関数**。

1. 正しい台帳版であること、12件のID重複・欠落がないこと
2. 現在の12件がPENDINGであることと、仮に変更したときに決定記録の根拠/担当ロールが揃っていること
3. 募集・保存・録音・採点・公開について明示的な禁止フラグがあること
4. 実施開始・収集済みの状態が誤って記されていないこと
5. 偽装された「APPROVED」や承認証拠のない決定を審査準備完了と判定しないこと

返却する`authorized`は、**設計上どの入力でも`false`**。12件の記録が埋まっても`manualReviewEligible:true`は**人間の審査を申請できる**意味に限定される。外部の実施承認・参加者ごとの同意に代わるものではない。

検査コマンド：

```sh
node --test scripts/test-a05-research-g1.mjs
```

テストのPASSは運用文書の整合・保護境界をチェックしたという意味であり、法律上・倫理上の適合審査や参加者の同意が完了したことを示さない。

## 5. Go/No-Go決定の順番

- **GO（準備文書の整理）**：台帳12件をそれぞれ根拠付きで確定し、人間の承認者と実施責任者が内容を審査する。
- **NO-GO（参加者に接触）**：台帳PENDING、窓口未定、保存先未定、同意文案未承認のいずれかがある間は実施しない。
- **NO-GO（実アプリや採点の変更）**：研究運用が承認されても、v2質問セット採用・E軸採点変更・製品公開の決裁は別。D-35/D-36の候補やD-37の割付が採用済みになるわけではない。
- **GO（次の準備作業）**：仮想データでの同意・保存・削除フローの机上試験、担当者の審査用資料調整。**個人データを使った検証は行わない**。
