### 優先して解消する4つのブロッカー

**AC-05/14｜本人照合とトークンの性質**：研究IDや連番を知っているだけで本人だと断定しない。撤回のための秘密を採用するなら、発行・保管・本人への配布・盗難/再使用・無効化・誤対象削除・紛失時対応を審査する。D-41の `FIXTURE_MATCH` は**本物の認証ではない**。

**AC-06/13｜実際の消去範囲**：暗号化を採用予定の端末・アクセス権・バックアップ・同期・復元履歴を確定し、**架空データで**消去手順と復旧不能性の確認方法を検討する。端末やクラウドを採用する前に、生成・複製・バックアップの各経路を洗い出す。純粋関数の論理マーカーが消えても実消去ではない。

**AC-08/15｜30日を越えない運用**：各面接日を起算点に、期限前倒しの撤回、期限到来、端末停止・休日・オフライン・実行失敗と再試行を想定する。期限到来時点で消えたという**推測**で利用者に完了を通知しない。具体的な日付・時刻（タイムゾーン）と運用監視・失敗時連絡は正式なG1審査が必要。

**AC-03/09/16｜撤回可能期間と説明の整合**：「個票は30日以内に保持終了」という提案と「30日間は本人の削除請求に必ず対応できる」という**未検証の約束**は同義ではない。照合不能・紛失・請求の受付期限・削除確認ができない場合を参加者向け説明に明記する。

## 3. 机上受入パターンと実際の受入の区別

| シナリオ | 机上で確認できること | 実運用で追加の証拠が必要なこと |
|---|---|---|
| 同意なし／拒否 | 記録不可と判定する契約 | 実際の画面/説明同意が保存前に有効か |
| 仮の照合一致／不一致 | 文字列のテスト用一致・不一致を機械処理しないこと | 秘密生成・安全な配布・漏えい・試行制限・再使用の制御 |
| 面接後14日 | 架空の連絡先マーカーが期限切れ | 端末の連絡先データとバックアップの実消去 |
| 面接後29日 | 30日案では対応表とメモの存在をモデル化 | 対象の特定・人の決裁・本人照合・削除失敗対応 |
| **面接後30日** | 30日案では対応表/メモをともに期限切れ | 実際の削除監査、キャッシュ/同期/バックアップの残存検査 |
| 面接後31日 | 90日メモが残らないモデル | すべての媒体で実際に残っていないという検証 |
| 対応表が先に消える方式 | 30/90の矛盾を検査で拒否する | 採用案・保存構造の責任者判断 |
| 調査辞退／撤回 | 架空マーカーと状態遷移を安全に扱うこと | 撤回者と対象レコードの対応確認、通知と監査 |

**不合格の判断**：原本かバックアップの片方だけで消去が確認できない、撤回手段を他人が推測可能、失効したIDで削除済と返す、データの外部送信を把握できない、責任者が実在しない、適用規程が未確認のうちは、**研究開始不可**のままにする。
