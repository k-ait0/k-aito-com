# K. Aito Analytics｜DWZ・Personal Lab・Analytics Core 横断差異監査 v0.1

**監査日：2026-11-13（JST）｜対象：研究ブランチのみ｜本番・商用使用未承認**

## 結論

各計算系は単に命名や表示が違うのではなく、月次の適用順、収支相殺、支出優先順位、売却方法、インフレ参照時点、丸め単位、リバランスの実行日、イベント期間の閉区間/半開区間、欠損データの計数が相違する。**全エンジンの結果を無条件に等価と扱うことは不可。**

対象実装（同研究ブランチ上で比較）：

- DWZ R4 v16.9の固定研究用simulateOne抜粋：`research/analytics/fixtures/dwz_simulateOne_r4_v16_9_research_fixture.js`。別の本番DWZエンジン全体や現在版の代表とは断定しない。専用fixtureで確認された単一資産処理のみ。
- Personal Lab v0.5：`research/analytics/personal-lab/index.html`（価格水準・2資産、浮動小数円）。
- Analytics Core v0.7：`lib/analytics/cashflow-core.cjs`、`portfolio-core.cjs`、`rolling-portfolio-lifecycle.cjs`（月次収益率・整数円・最大12資産）。
- 統合アダプター：`lib/analytics/personal-multiasset-bridge.cjs`。
- ローカル画面：`research/analytics/personal-lab/multiasset.client.js`。実装済みの個人向け12資産版。

主な根拠：
- 再現性のある12項目の例：`scripts/test-analytics-cross-engine-divergence-audit.cjs`。
- 資産数1・2・3・5・8・12、投資期間とデータ検査：`scripts/test-analytics-personal-multiasset-bridge.cjs`。
- GitHub Actions **成功**：https://github.com/k-ait0/k-aito-com/actions/runs/43250606244

全テストは**合成データのみ**。相場データ・税務法令・個別商品の経費を実測して「正式に正しい」と認めたものではない。

### 数値一致できる条件も特定

月初入金→月初引出→月次騰落、単一資産、整数円、同じ月間収益率・同じ丸めに条件を絞ると、`cashflow-core`と`portfolio-core`は以下の例で一致する。

- 初期120円、月初積立10円、月初支出5円、月次収益+10% → 両者とも期末138円。
- 全192件のDWZ固定`simulateOne`とPersonal単一資産（税なし・積立/年金なし）との整合テストも継続成功。ただし**DWZ全仕様の包括的一致ではない**。

## B. 監査中に発見した、修正すべき実装の問題と対応

### F01 不正な市場レコードを欠損扱いする可能性（修正済み）

新ブリッジのローリング計算は、元の市場データの出典区分異常・並び順異常・推計値を、計算可能な窓の除外として隠してしまう余地があった。

- `rollingPersonalMultiAsset`の入口で、全期間に対して`validateMarketSeries`（推計/代理/観測混在、非有限リターン、不正な順序は停止）を呼び出すよう変更。
- 月次欠損だけは連続月ブロックを分割し、その窓を除外。CPIも期末・期首基準に必要な全月が揃う場合だけ計算。
- ローリング開始窓が1件もない場合でも、計画・市場・保有比率の妥当性を評価する。

### F02 実測市場と合成CPIの無表示混合（修正済み）

月次実質化を要求するときに市場の由来`OBSERVED`/`SYNTHETIC`とCPIの由来が一致しなければエラーに変更。単に値が正しく、月が連続しているだけでは同じ実測系列と断定しない。

### F03 暦月の観測欠損数を少なく見せる（修正済み）

旧Coreの理論暦月開始窓に対して、新ブリッジは実際に存在する行数から計算した開始候補しか数えていなかった。

- `row_based_candidates`、`excluded_windows_due_to_gap_or_cpi`と、`theoretical_calendar_windows`、`excluded_calendar_windows_due_to_gap_or_cpi`、`observed_calendar_gap_boundaries`を分離して記録。
- 実際の例：65行・60か月判定・途中1か月欠損では、行ベース候補6、暦月理論候補7、完全窓0。暦月基準の除外は7窓であって6窓ではない。
- UIのローリング補足に暦月基準の除外件数を表示。

### F04 本人入力の指数／CPIのラベル不正（修正済み）

同じ`INDEX_TOTAL_RETURN`でも単位が`JPY_PER_USD`のCSV、e-Stat全国CPIを自称して単位が別基準のCSVを通せる余地があった。

- 新12資産画面では指数の`unit=INDEX_TR`、JPY、`INDEX_TOTAL_RETURN`、`OBSERVED`、登録済み出典ID、正の指数値・固定系列メタデータ・SHA256形式を確認。
- 日本CPIでは`JP_CPI_HEADLINE_2025_LINKED`、`ESTAT`、`CPI_LEVEL`、`INDEX_2025_100`、`NOT_APPLICABLE`、`OBSERVED`とSHA形式を確認。
- **ただし形式のQAは出典を暗号学的に認証するものではない。** 本人の適法取得・原本の真正性は別審査。

### F05 バンドルの依存関係（修正済み）

F01の共通バリデータにより追加された`rolling-portfolio-lifecycle.cjs`を、オフライン単一HTMLのビルダーにも明示的に含めた。生成可能・ブラウザー評価可能な状態をCIで確認。

## C. 優先順位と推奨する統合契約

**P0：正しさのゲート**

1. 金融イベントの正式スキーマを設ける。支出・収入の**総額**を保持し、同月の相殺は最終キャッシュフローを求めるときに限定する。弁済順序（通常生活費・住宅修繕・税金等）を明示し、各費目の`due/paid/unfunded`を残す。
2. 月次位相を列挙型で固定：`MONTH_START`・`MONTH_END`。カレンダー年月が月間収益区間の開始を示すか終了を示すかも明記。DWZと旧PersonalのEND支出を無条件にMONTH_STARTへ換算しない。
3. 年金／給与の期間は`start_offset_months`含む・`end_offset_exclusive`含まないで統一する。ただしLegacyのinclusiveを読む場合はバージョン・マイグレーションが必須。自動黙換算禁止。
4. 金額の会計規則：整数円で入力・保有し、各資産の収益を円に丸めるタイミングを明記。資産分割による端数差を説明する。損益と現金保有の価格・為替・TR区分は別管理。
5. ローリングのデータ品質：暦月の理論窓・実観測窓・欠損除外を常時別表示。推計値や偽装出典は「欠損」として隠さない。
6. **税・NISA計算の導入前に**課税口座／非課税口座、取得価額、売却ロット、配当、諸費用をモデル化する。既存Coreの時価だけから個別の譲渡益課税を推算しない。

**P1：仕様選択が必要**

- 売却順序を`CASH_FIRST/RISK_FIRST/PRO_RATA`から選択できるようにするか、比例のみと明示して旧版との比較範囲を狭める。
- 最終月のリバランスを「期末保有をターゲット配分にする売買」として実行するか、投資期間終了時の不要な売買として省くか、UIで意味を説明して決める。
- 比較年数より後のイベントを`SKIPPED_AFTER_HORIZON`として可視化するか、現在のように条件不正として計算停止するかを正式決定する。10年/20年/30年の同じ人生設計の比較時は特に問題。
- 課税・費用なしの研究gross Coreと、将来の実運用net Coreを明確に分ける。

**公開・本番への移行は今回していない。** main、FINOWA、公開Analytics、DWZ本体・既存研究ブランチの他の箇所、権利未承認の市場データ、秘密鍵などは無変更。データ提供元の未取得TRは未取得として維持する。
