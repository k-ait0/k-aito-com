## 1. D-55で確認した技術的な問題

### 1-1. 空の端末でも不整合バックアップが「計画段階」と表示される

D-53の`inspectA05RestorePlan()`は、復元を実行しない設計を維持していたものの、端末内の保存領域が空であれば、バックアップに旧版履歴・破損履歴・互換性のない下書き・保護対象の移行情報が含まれていても、全体の`status`に`PLAN_ONLY_REQUIRES_HUMAN_REVIEW`を返す場合があった。

`blockers`には個別の不整合が記録されるため、**実際の復元許可やデータ書込みには直結しなかった**が、利用者と後続のレビュー担当者が全体状態を好意的に解釈する危険があった。

**修正**：互換性に関するブロッカーがある場合は、空端末であっても`BLOCKED_BACKUP_INCOMPATIBLE`へ明示的に分類する。既存端末にレコードがある場合は`BLOCKED_EXISTING_LOCAL_DATA`、壊れたJSON形式なら`BLOCKED_STRUCTURE`を引き続き優先する。非破壊の正常な架空データであっても`PLAN_ONLY_REQUIRES_HUMAN_REVIEW`は**あくまで計画上の表現**で、復元許可ではない。

`app.mjs`のバックアッププレビューにも、互換性不明の下書き・保護対象について「復元候補にできない」という明示警告を追加。バックアップ内にある以前の「保存同意」も、現在の端末へ自動引継ぎできないと説明する。回答・氏名・個別IDは表示しない。

**不変条件**：`restoreAuthorized:false`、`restoreImplemented:false`、`anyDataWritten:false`。保存データの実インポート、既存レコードの上書き・削除、JSON署名照合は実装しない。

### 1-2. 文書だけのPR更新でレビュー台帳が検証されない

D-54のレビュー台帳はファイル全件を登録するが、既存GitHub Actionsのパストリガーは`projects/kidp/**`やA05用テスト/スクリプト等に限定され、**`docs/A05_D*.md/json`だけを修正したPR更新では検査が起動しなかった**。

このままだと、資料や新規文書の追加によってPRの変更ファイルが増えても「PR差分全件＝レビュー台帳」の検査が実行されず、`NOT_REVIEWED`の登録漏れが見過ごされる。

**修正**：既存`kidp-wave-a-browser-qa.yml`のPRパストリガーへ`docs/A05_D*.md/json`を追加。PR #61であれば、**文書だけの変更でも`test-a05-pr-review-manifest.mjs`を実行**し、PR merge参照の全差分と台帳を照合する。A05実装・QAに関係しない文書のみの変更では、重いPlaywrightインストール/Chromium起動を省く。A05ソースを変更した場合は、従来どおりNode＋Chromium実ブラウザ検査を実施する。

- **新しいジョブやワークフローは追加しない**。
- PR #61に限定した監査条件のため、他PRにPR #61固有の台帳を要求しない。
- 上記パストリガーはA05文書に対象を限定する。既存KIDPサイトの通常のQA経路は維持する。
